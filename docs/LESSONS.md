# 经验和教训

这些内容帮助后续开发者理解项目，不新增流程、工具或测试制度。

## 曾经反复偏移的地方

1. **把每秒帧率理解成每次总张数。** 用户说3 / 6 / 9连拍是fps，不是一次按快门只拍3 / 6 / 9张。目标要求原生镜间快门，不能暗换电子快门。
2. **把UI标签或标称数字当性能功能。** 修改模式判断和帧率字符串，不会自动补齐传感器时序、RAW格式、校准、缓冲所有权和3FR保存链路。
3. **拿历史结果证明新候选。** 旧候选安装过、某次root读回成功、旧桌面检查通过，都不能证明当前新代码的实际行为。
4. **把推测讲成定位完成。** “一张不保存、一直正在写入”可以指导定位，却不能凭现象确认JLS、frame ID或SSD哪个环节坏了。缺少对应计数、事件或原件时标注假设。
5. **混淆平台故障和机身故障。** Windows长路径、MSYS启动成本、电脑等待和管道未关闭，都可能使测试失败；必须先说明失败停在哪一步。
6. **准备阶段超时，却声称保护测试已覆盖。** 没到故障注入点时，后续恢复或拒绝断言是NOT_RUN，不是PASS。
7. **过度泛化检查和报告。** 工具数量、目标数量、耗时、报告文件都不是可用成果；每项工作须对应一个实际缺口。发布资料整理不重跑固件全套。
8. **一个组件通过就结束。** 本地阶段通过只是进展；对于安装交付仍要闭合真实菜单、进入 / 返回、原厂拍摄保存、启动与撤回。
9. **身份不等于全部权限。** UID0、`su`域、维护域、init启动域不是同一运行环境；读取权限与文件操作权限不能互相替代。
10. **完成后遗漏基础复检。** 近期草稿实际发现“先执行源代码再验哈希”和重复读取未绑定字节；这类错误应保留为永久反例，不用漂亮报告掩盖。

## 值得保留的路线

- 从已有成功项目学习真实加载方式：原厂底层保留、独立库与QML接入原厂GUI、原厂菜单增加入口、独立配置和可撤回；当前先不动拍摄底层。
- 源码、观察、历史设备记录与当前实机验收分别标注来源，避免机型和提交混用。
- 最新修正只动对应故障，相关验证用于修正开发；完整候选才处理适用发布检查。
- 照片、校准、官方恢复路径和失败原件始终保留。减少无关流程，不删除必要证据。
- 后台本地模型提供建议，Codex审查角色不绑定6.1或某一个未来模型；模型输出不自动执行、写相机或标记通过。

## 现阶段不应承诺的东西

没有完整破解机身源码；没有证实16-bit 3fps、14-bit 6/9fps或类似索尼的AF；没有本候选实机安装验收，也没有无损、全函数、连续8小时日志追踪证明。保留这些目标与研究不等于它们已经实现。
